# Wiki批量操作（重命名/重编号/链接迁移/批量填充）

## Overview

对Obsidian/Wiki做**批量结构性操作**时的安全工作流：案例或实体页重命名、重编号、全库wikilink迁移、反向链接批量补齐、从原始材料批量填充页面。这些操作风险高（一次失误可致全库死链或文件丢失），本技能固化已验证的流程和本会话踩过的坑。

与 `legal-wiki-audit-repair`（审计与分批修复）、`wiki-content-completeness`（内容完整性）协同；批量操作完成后必须跑它们的验收标准。

> 跨案比较页（comparisons/）的6段格式规范与链接纪律见 `references/comparison-page-format.md`（OPT-008用户验收固化）。

## When to Use

- “案例文件按编号重命名”“页面标题标号”；**注意：用户要的是文件名编号（`案例N-标题.md`），不是页面标题里加编号**——曾明确纠正“我不是让你在页面里面标案例1 案例2，是让你在页面文件的命名上”；
- “案例分成几个文件夹”“按优先级分组”；
- “全库链接要跟着新文件名走”；
- “给这N个页面补反向链接”“批量填充剩余页面”。

## 一、批量重命名/重编号安全流程

1. **建映射**：`旧文件名 → 新文件名`（含编号、分组），存 `.maintenance/<任务名>-<日期>/` 下（**不要只存 /tmp**，系统会清理，丢失后需从原始材料重建）。
2. **校验映射**：新旧名无重复、无缺失、编号连续；**逐条标记 old==new 的同名项**。
3. **备份**：重命名前把全部涉及文件复制到备份目录（本会话靠备份救回一次文件被误删事故）。
4. **执行重命名**（Python脚本）：
   - old != new：写新文件 → 校验成功 → 删旧文件；
   - **old == new：只更新内容，绝不执行 unlink**（“写新→删旧”会让同名文件被删除，数据丢失）。
5. **全库wikilink替换**：Obsidian wikilink 按**文件名（不含路径、不含.md）全局解析**：
   - 移动文件到子文件夹 → **不需要改任何链接**；
   - 重命名文件 → **必须全库替换** `[[旧名]]`→`[[新名]]`，且用 `[[旧名]]` 和 `[[旧名|` 两种形式都替换。
6. **验收**：全库 rglob 所有 .md，提取 `[[...]]`，与所有页面stem集合比对 → 死链0；再查 `案例N-M-`、`案例N--` 等错误模式残留。

## 二、从文件名提取编号：必须用正则

**禁止字符切片** `stem[3:]`：中文文件名按字符切片会错位（`"案例13-xxx"[3:]="3-xxx"`），拼出 `[[案例13-3-xxx]]` 假链接。

正确写法：

```python
m = re.match(r'^案例(\d+)-(.*)$', stem)
if m: n, title = int(m.group(1)), m.group(2)
```

反向链接插入时同理，**直接引用完整 stem**（`[[{cases[a]}]]`），不要拼 `'案例{a}-' + cases[a][3:]`。

## 二点五、重编号后新写页面的链接编号校验（本会话10个坏链接的教训）

**场景**：文件已重分类重编号（如田林案旧92→新53），但后续批量填充页面时，页面正文里引用案例仍按**旧编号记忆**写链接（`[[案例92-王某诉锦州…]]`）——编号偏移，链接全死。

**必须流程**（每次批量填充页面后执行，不能只靠"写的时候小心"）：

1. 从三目录真实文件名构建索引 `real[n]=完整stem`（含case_id）。
2. 对每个新写/填充的页面，扫描 `[[案例N-标题]]`：
   - `N in real and real[N]==目标` → 正确；
   - `N in real but real[N]!=目标` → **编号对但标题错**（该编号已被别的案例占用）；
   - `N not in real` → 编号不存在，**按标题前10字关键词**在real.values()中找候选。
3. 用`旧链接串→真实文件名`映射批量替换；替换后复跑死链=0、错误模式残留=0。
4. **反向补链脚本的 `stem[3:]` bug 会产生两种错误变体**：`案例N-M-标题`（多插数字）和 `案例N--标题`（双连字符）——验收正则要同时查两种：`\[\[案例\d+-\d+-` 和 `\[\[案例\d+--`。

## 三、反向链接批量补齐

1. 先统计单向链接 `(a→b 存在但 b→a 不存在)`。
2. 对每个目标页 b：在 `## 与其他案例的关联` 章节**末尾**追加 `- 与[[案例a-…]]的关联：…`。
3. **章节边界**：先找 `## 与其他案例的关联` 起始，再找下一个 `\n## ` 作为结束；无该章节时插到 `## 相关概念` 前或EOF。**插入位置算错会把后续标题吞进链接**（如 `[[案例92-…某工## 相关概念`）。
4. **去重**：追加前检查该章节是否已含 `案例a-`，避免整段重复。
5. **自链接排除（26处自链接事故的教训）**：批量补反向链接时必须跳过 `目标a == 当前页面自身` 的条目。曾因未排除自身，给26个案例页插入了 `- [[案例74-韩某…]]：两案均为…` 式自链接——链接指向自己、描述内容却是别的案例的（错位），页面里出现“自己关联自己”的无效条目。清理方法是正则删整行：`^- \[\[(<自身stem>)(?:\|[^\]]*)?\]\][^\n]*\n?`。
6. **变体标题**：检测“与底稿的关联”时注意变体（如“与检例205号底稿的关联”），用包含判断而非精确匹配，避免误报。
7. 补完后复跑：单向0、死链0。
8. **中心节点（底稿页）反向导航**：全部案例页都设有"与底稿的关联"章节后，底稿页应新增 `## 与案例的关联（底稿←案例）` 章节，按三层分组列出全部121个案例的wikilink（`[[案例N-标题]]` 整行列表），使中心节点成为反向可达的导航页——这是"底稿是中心节点"要求的完成形态。

## 四、批量填充页面：材料决定深度

批量填充案例页时，**深度由原始材料决定**，用户接受“材料决定深度”但反对凭空补写裁判理由：

| 材料类型 | 篇幅 | 页面深度 |
|---|---|---|
| 公报案例/判决书全文 | 3000–10000+字 | 详细页（7–8章齐全） |
| 地方法院典型案例 | 平均约1400字 | 中等页 |
| 极简案例 | <800字 | 如实简写 |

分层标准（法学引注需要案号）：材料>2000字 → 核心组（优先研究引用）；有完整案号 → 辅助组（可引用）；无案号典型案例 → 参考组（仅裁判观点参考）。

## 四之五、叙述中的案例提及也要链接化（用户明确要求）

比较页/综合页**正文叙述里提到的案例名**（如"韩老汉案""七台河案"）也必须加wikilink——用户明确要求"所有的案例要加上链接"，不只是案例表。用**显示文本链接**保持可读性：

```python
s = s.replace('韩老汉案', '[[案例102-超龄农民工午休时突发疾病48小时内经抢救无效死亡视同工伤|韩老汉案]]')
```

- 先建 `提及词 → (完整文件名, 显示文本)` 映射，覆盖**案例表之外的叙述提及**；
- 验收：把页面中所有 `[[…]]` 替换为占位符后，扫描剩余"XX案"模式，确认无未链接案例名（排除"本案/案件/案例/案由"等通用词）；
- 注意长提及词先替换（如"昌邑三案"→"昌邑案"），避免子串冲突。

## 四之六、表格单元格内的带别名wikilink：必须用 `&#124;`（用户发现"空格子"的根因）

**问题**：Markdown表格单元格内写 `[[案例73-颜某某…|颜某某案]]`，`|` 会被表格解析器当成列分隔符，整行被撕裂成2-4列，Obsidian渲染出"空格子/错位"；`\|` 转义在Obsidian的wikilink里也不被识别为别名分隔符。

**正确写法**：别名管道符改用HTML实体 `&#124;`：

```
| **死亡标准** | 昌邑/[[案例73-颜某某诉…&#124;颜某某案]]采脑死亡标准 |
```

**验收**：全库扫描所有markdown表格，统计每张表各行列数（分割前先把 `&#124;` 替换为占位符再 `split('|')`），列数不齐=0。

**另注意**：`[[A|[[B|C]]]]` 嵌套链接是批量字符串补链对已链接文本二次包裹产生的——补链脚本应对"已含 `[[` 的文本"跳过，或用负向断言避免在链接内替换。

## 六、论文初稿引用案例整合（DRAFT20模式）

**场景**：用户已写论文初稿、引用N个案例（提供《初稿引用的N个案例原文完整版.docx》），希望知识库支撑后续改稿。**用户战略**：暂不放初稿进库 → 知识库搭建完成 → AI读库从零写大纲 → 与初稿对比修改。

**关键洞察：先勘察再摄入，避免重复建页**。20案例勘察后发现全部已在121案库中（材料同源），无需重复摄入——直接做增量标注。

工作流：
1. **提取目录**：读docx前40段，解析"案例目录"区的N个标题（按脚注[1]-[N]顺序）。
2. **匹配库内编号**：用标题关键词（人名+诉+机构）扫描三目录文件名，逐一映射 `脚注号→库内案例N`。全部命中则告知用户"无需摄入"；有未命中的才考虑补建。
3. **⚠️ 不做脚注标注（用户明确纠正过）**：用户说"我都没给你论文，你怎么做脚注呢？"——docx里的"对应论文脚注[1]-[N]/论文原脚注"只是汇编整理者的标注，不是用户论文的真实脚注；论文原文未入库前，**禁止在案例页添加"论文脚注/原脚注引文"章节**。20案全部在库时只做：
   - 建导航页 `queries/论文初稿引用的N个核心案例.md`：案例链接+核心争点+层级 对照表（**不写脚注编号**，注明"脚注以初稿实际编号为准"）；
   - 挂载到index.md Research Design区。
4. **可选增量**：docx中"论文原脚注"字段含完整案号（如（2023）京0116行初196号），若库内页面基本信息缺案号可据此补全——只补基本信息，不建脚注章节。
5. **验收**：导航页死链0、案例页未被添加脚注章节。

**改稿阶段衔接**：导航页即"改稿工作流"入口——论文某处脚注→导航页定位案例→案例页全部研究分析→引用文献支撑。

## 七、环境陷阱

- **目录名可能被外部改名**：Obsidian 里文件夹可能被加上序号前缀（如“1. 核心案例”）。脚本路径报 `FileNotFoundError` 时先 `ls` 确认实际目录名，不要假设。
- **目录分层/拆层重排（NORM-REORG模式）**：当用户要求按新分类法重排子目录（如法规范层按效力层级拆成 `1. 法律/ 2. 行政法规/ 3. 部门规章/ 4. 司法解释/ ...`）时，直接 `mv` 整个子目录即可——**Obsidian wikilink 按文件名解析，移动目录不破坏任何链接**；重排后旧路径引用只会残留在 log.md/台账的历史记录中（假阳性，不要改），但 SCHEMA.md 与 index.md 的目录结构说明必须同步更新。`mv` 前先确认目标目录不存在同名文件。
- **/tmp 会被系统清理**：解析中间产物（span、映射、parsed json）存项目内（`.maintenance/` 或工作目录），丢失后从原始docx重建耗时。
- **execute_code 被拦截时**：改用 terminal + heredoc 运行 python3（`python3 << 'EOF' … EOF`），本会话验证可用。
- **read_file 对中文密集 .md 误判为 binary**：读wiki页面/索引txt报 "Binary file - cannot display"（文件实际是合法UTF-8、无null字节）——用 python3 读写，不要用 read_file/`cat` 依赖其文本显示。
- **长中文 python 脚本用 heredoc 会偶发编码失败**：`SyntaxError: Non-UTF-8 code starting with '\xe6' in file <stdin>`——heredoc 只适合短脚本；长脚本（含大量中文串的列表/映射）先 `write_file` 存成 .py 再 `python3 文件` 运行。

## 八、批量操作后的格式审计（FORMAT-AUDIT固化）

批量填充/重命名完成后做全库格式审计时，注意以下修复规则与误报甄别：

**修复规则：**

1. **统一YAML title与页面#标题**：以页面#标题为准改YAML。页面标题含中文引号（`"合理时间"`）时，**不要用英文双引号包裹**（`title: "上下班途中"合理时间"的认定边界"` 会YAML解析失败），直接中文引号裸写；同时把页面#标题的英文引号统一为中文引号。
2. **批量补"标题后无空行"**：匹配 `^#{1,6} .+` 标题行，下一行非空且非 `#`/```（代码块）/`|`（表格）开头才补空行——**必须跳过表格和代码块**。
3. **审计脚本先自检**：大规模数字异常（如YAML错误从0变175）先怀疑脚本自身（漏import、正则误配），用最小样本人工核对后再改数据。

**误报甄别（不要当问题修）：**

- **维护文档豁免**：`SCHEMA.md`/`log.md`/台账/index.md 无frontmatter、标题后无空行均属正常；格式检查只针对正式内容页。
- **变体章节不是缺章节**：最高检指导性案例本体页（检例205号李某案、检例236号邹某某案）用"诉讼程序与裁判观点/争议焦点/检察机关履职过程"等变体章节，缺"程序历程/主要争议焦点"检测是误报。
- **英文残留甄别**：案例页的 `Wiki`/`cases` 来自 `raw/cases/` 路径和来源说明（有意）；论文页的美国判例引注和DOI属内容性英文——保留，只清理正文无意义英文。
- **台账"空章节"**：标题后空行接子标题不是空章节；`[[案例-2005-松业石料厂…]]` 含省略号是示例文字不是死链。

## 九、论文页"与案例的关联"章节批量插入（PAPER-CASE-LINK模式）

**场景**：给N篇论文页新增 `## 与案例的关联` 章节——论文核心论点与库内案例裁判要旨的"观点↔案例主旨"印证关系（**非引用关系**）。2026-08批次：侯玲玲篇为已完成范本，8篇论文批量完成（共9/24篇），剩余论文可沿用。用户明确规则：**严格基于要旨文本判断对应关系，不得臆造**。

1. **数据源**：`/tmp/papers_core_points.json`（键=论文文件名stem，值为编号论点）、`/tmp/case_yaozhi_index.json`（121案例裁判要旨，键=案例**完整stem含年份**）。先通读全部要旨再逐篇匹配；对应关系**严格基于要旨文本，不得臆造**。制度构建类论文（新就业形态等）**先查库内新业态案例**（骑手/送餐员/快递员：案例22、24、45、50），有真实对应就写对应、确实无对应才写"本论文为制度构建研究，与个案要旨直接对应较少"（本次8篇均有匹配，未用兜底句）；可用论文页自身`## 引用案例`章节交叉验证对应真实性。主题→案例候选速查见 `references/paper-case-theme-mapping.md`。
2. **格式**（范本：侯玲玲篇）：
   - 插入位置：`## 与其他论文的关联` 标题**之前**（插入前断言该anchor count==1且页内无既有"与案例的关联"章节）；
   - 说明行：`> 按"观点↔案例主旨"对应建立（2026-08试点）：论文核心论点与库内案例裁判要旨的印证关系，非引用关系。`（**以侯玲玲篇实际文本为准，带"试点"二字**）；
   - 条目：`1. **观点N（简要）** ↔ [[案例N-YYYY-完整stem]]——对应理由（60-150字）`；观点N编号对齐 papers_core_points.json 中的论点序号；**链接必须整串复制索引key（含年份）**；一个编号条目可容纳2个案例链接（侯玲玲范本第2条即如此）。
3. **插入方法**：python3 读全文 → 字符串replace(anchor, section+anchor) → 写回；其他章节零改动。同一案例可被多篇论文引用（如江苏某机电29号案被3篇论文引用，属正常）。
4. **验收**：跑 `scripts/verify_case_link_sections.py <wiki根> <论文文件...>`——新章节位置在"与其他论文的关联"前、新章节内死链0（用 entities/案例 三子目录 rglob 真实stem比对）、每条理由60-150字、说明行存在、其余章节标题序列不变。
5. **坑**：
   - 论文页其他章节（引用案例等）可能存在**既有死链**（匿名化别名链接如 `[[案例1-2003-何文良…|何某某…]]`、`[[案例2-2005-松业石料厂…|…劳保局…]]` 与实际stem不符）——**不在本次范围，不修**，只向用户报告留作后续审计线索；
   - 案例文件分布在 entities/案例 的"1. 核心案例/2. 辅助案例/3. 参考案例"子目录，收集stem必须 rglob。

## 九之五、案例↔论文纯链接核验修复批（LINK-VERIFY模式，2026-08批次实测）

## 九之六、案例页→论文页批量同步（CASE-PAPER-SYNC模式，2026-08批次1实测）

**场景**：案例页`## 与论文的关联`已有完整格式化条目（`- **论文名**：本文观点N（简要）以本案要旨为支撑——理由`），但论文页`## 与案例的关联`缺对应回链（单向），需按批把案例页条目同步成论文页条目（双向对称）。用户分批指定论文（"第1批：胡京、谭秋勤、王东伟-司法审查、王敏"——后续批次沿用）。本批4篇论文：案例页129条 → 补30条（胡京+11、谭秋勤+1、王东伟-司法审查+17、王敏+1），其余99条先前批次已回链。

1. **提取**：rglob entities/案例 三子目录；章节切分 `re.search(r"^## 与论文的关联\s*\n(.*?)(?=^## )", text, re.M|re.S)`；逐行匹配 `- **<论文完整stem>**：`（**不带.md**）。**同名作者多论文必须整名匹配**（王东伟有"工伤认定行为的司法审查研究"与"论工伤认定行政诉讼案件中的举证责任"两篇，只匹配目标篇，严禁 `startswith('王东伟')`）。
2. **解析条目**：观点=`re.search(r"本文观点\s*(\d+)?\s*（(.*?)）(?=以本案)", entry)`——lookahead `(?=以本案)` 天然吞掉观点括号内的嵌套括号（如`（四维路径解释不确定法律概念（社会生活一般观念））`）；理由=`re.search(r"以本案(?:要旨)?为支撑——(.*)$", entry)`——`以本案要旨为支撑`与`以本案为支撑`两种表述都要兼容；无观点编号→写`**本文观点**`。
3. **去重**：论文页章节内**全部`[[…]]`链接**组成stem集合——一条论文页条目可含多个案例链接（胡京#9同时链案例52与87），按条目数判重会漏判；案例页条目stem不在集合中才追加。
4. **追加**：编号=章节现有最大编号+1（`re.findall(r"^(\d+)\.\s", section, re.M)`取max；编号跨空行分组也无妨）；新条目 `N. **观点N（简要）** ↔ [[案例完整stem]]——理由`；插入位置=章节最后一个非空行之后、保留其后的空行结构（不吞下一个`## `标题，4篇论文该章节后均为`## 与其他论文的关联`）；理由直接沿用案例页条目原文（已含"印证论文/正是论文所述"等论文视角表述），个别微调（案例60-胡京："这一法律原点"→"论文所述…法律原点"），CJK字数60-150校验（`[\u4e00-\u9fff…]`计数）。
5. **只追加不修改**：写前逐文件备份到 `.maintenance/<任务>/before_batchN/`；验收断言旧章节全文（rstrip后）仍在文件中（子串包含即未改动）。
6. **验收**：①逐论文复扫：案例页全部条目stem ⊆ 论文页章节stem，缺失=0；②编号连续；③理由字数范围；④备份对比旧章节完整保留。报告=每篇论文追加条数。
7. **脚本**：`scripts/sync_paper_case_links.py`——改顶部 WIKI/TARGETS 即可复用，支持 `DRY_RUN=1` 先试跑（本批实测流程：提取→解析→判缺→备份→追加→四重验收）。

## 九之七、概念页"规范依据"小节批量插入（NORM-REFERENCE模式，2026-08批次2实测）

**场景**：给概念页/比较页新增 `## 规范依据` 小节——列出该概念对应的法规范页wikilink（如上下班途中→条例14条6项+法释2014-9号6条；不确定概念→三工认定总纲；一般条款→条例14-16条+批复答复；工时→条例14条1项+行诉法；劳动关系→批复答复-劳动关系与工伤认定主体+条例18条）。用户分批下达（"第2批"等），每页2-4条。

## 十、YAML字段批量插入（USAGE-MARK模式，2026-08实测）

场景：给全部案例页YAML加统一字段（如 `usage: 详析/脚注/备用`），并新建配套清单页。
